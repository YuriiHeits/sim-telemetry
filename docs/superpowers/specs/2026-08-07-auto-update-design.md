# Автооновлення StintLogger з GitHub Releases

Дата: 2026-08-07
Статус: спека, погоджена усно, до реалізації

## Мета

Логер роздається як `StintLogger.exe` через GitHub Releases. Зараз він не знає
власної версії й ніяк не повідомляє, що вийшла нова — користувач лишається на тій
збірці, яку колись скачав. Мета: застосунок перевіряє реліз, і, якщо той новіший,
завантажує й підмінює себе сам.

## Рішення, які визначили решту

1. **Повне автооновлення, не лише повідомлення.** Свідомий вибір власника; ціна —
   самозаміна бінарника, тому решта рішень цієї спеки присвячена тому, щоб її
   можна було перевірити й відкотити.
2. **Гейт перед підміною: завантажений exe мусить сам назвати свою версію.** Він
   запускається як `--version` і має вивести саме ту версію, яку обіцяв реліз.
   Не вивів, впав, не починається з `MZ` — оновлення скасовується, старий exe не
   чіпається. Без цього гейта самозаміна означає «мовчки замінити робочий
   інструмент на будь-що, що прилетіло по мережі».
3. **Підміна перейменуванням, без bat-хелпера.** Windows не дає перезаписати
   запущений exe, але дає його перейменувати. Хелпер-скрипт був би четвертим
   процесом, який неможливо накрити тестом.
4. **Старий бінарник видаляється лише після успішного старту нового.** Доки новий
   не піднявся, `StintLogger.old.exe` лежить поряд і відкат можливий.
5. **Мережа ніколи не блокує запуск.** Перевірка — у daemon-потоці, з таймаутом,
   з тихим провалом. Логер мусить працювати без інтернету так само, як зараз.

## Не входить в обсяг

- Канали (beta/stable), відкат з UI, оновлення на вимогу за розкладом.
- Підпис коду й перевірка підпису. Гейт — це `--version`, не сертифікат.
- Оновлення python-версії (`.pyw`): вона живе в git, там `git pull`.
- Дельта-оновлення. Качаємо весь exe, це ~26 МБ.

## 1. Версія

- `APP_VERSION = "1.1.0"` у `stint_logger.pyw` поряд з `APP_NAME`. Назва саме
  така, бо цю ж константу вже додає план `2026-08-06-sim-setup-skill.md` для
  `state.json` — двох констант версії у файлі бути не повинно.
- Аргумент `--version`: друкує `StintLogger 1.1.0` у stdout і виходить з кодом 0,
  **не піднімаючи GUI й не торкаючись single-instance ключа**. Це і CLI-зручність,
  і той самий гейт з рішення 2.
- Версія показується в UI (рядок під заголовком) і в підказці іконки в треї.

## 2. Перевірка релізу

`GET https://api.github.com/repos/YuriiHeits/sim-telemetry/releases/latest`

- Заголовок `User-Agent: StintLogger/<VERSION>` — **обов'язковий**, GitHub
  віддає 403 без нього.
- Таймаут 5 с. Будь-яка помилка (немає мережі, 403, 404, зламаний JSON) → тихо
  нічого не робимо, у стані лишається «перевірка не вдалася».
- З відповіді беремо `tag_name` і серед `assets` — той, чий `name` дорівнює
  `StintLogger.exe`, звідти `browser_download_url` і `size`.
- Ліміт GitHub — 60 запросів/год на IP без токена. Перевірка раз на запуск і
  пунктом у треї в цей ліміт вкладається з запасом.
- HTTPS через `urllib.request` у frozen-збірці працює без додаткових залежностей:
  на Windows Python бере кореневі сертифікати з системного сховища.

Порівняння версій — власна функція `newer(a, b)` над `X.Y.Z` (кортеж цілих,
префікс `v` відрізається). Некоректний тег → вважаємо, що оновлення немає.

## 3. Завантаження

- Тека `%LOCALAPPDATA%\StintLogger\update\`, а не поряд з exe: той може лежати в
  теці без прав на запис (Program Files, тека іншого користувача).
- Файл `StintLogger-<tag>.exe`. Якщо вже є з правильним розміром — не качаємо
  вдруге.
- Розмір мусить збігтися з `size` з API; не збігся — файл видаляється.
- Прогрес показується в UI рядком, без окремого вікна.

## 4. Гейт і підміна

Порядок операцій, кожен крок скасовує оновлення при провалі:

1. перші два байти завантаженого файлу — `MZ`
2. `subprocess` запускає `<завантажений> --version`, таймаут 15 с; stdout мусить
   містити версію з `tag_name`
3. поточний `sys.executable` → `StintLogger.old.exe` (`os.replace`, той самий том)
4. завантажений файл → на місце `sys.executable` (`shutil.move`)
5. `subprocess.Popen` нового exe з аргументом `--after-update`
6. поточний процес виходить (звільняючи single-instance ключ і трей)

Якщо крок 4 упав після кроку 3 — повертаємо `.old` назад на місце й скасовуємо.

Новий процес з `--after-update`:

- чекає, поки звільниться named mutex `StintLogger_singleton` — саме він, а не
  заголовок вікна, є single-instance ключем (`single_instance_ok()`,
  `stint_logger.pyw:870`; `FindWindowW` використовується лише щоб підняти наявне
  вікно). Мьютекс тримає процес, тому чекати треба виходу старого процесу:
  опитування `single_instance_ok()` до 10 с
- якщо за 10 с мьютекс не звільнився — новий процес **не** обходить single-instance
  захист, а йде звичайним шляхом і закривається. Оновлення при цьому вже
  застосоване: новий exe лежить на місці, користувач отримає його наступним
  запуском. Двох одночасних екземплярів не буває ні за яких обставин.
- піднімається як звичайно
- **після успішного старту** видаляє `StintLogger.old.exe`; не вийшло видалити
  (антивірус тримає файл) — не помилка, спробує наступний запуск

Прибирання `.old` при звичайному старті теж робиться: якщо файл лежить, а ми
запустилися — він більше не потрібен.

## 5. Автозапуск у реєстрі

Не змінюється: у `HKCU\...\Run` лежить шлях з тим самим іменем файлу, а ім'я
після підміни те саме. Спеціальної логіки не потрібно — але це треба перевірити
на живому автозапуску після першого оновлення.

## 6. Тести

Чисті функції — у `tests/test_update.py`:

- `newer()`: `1.0.0 < 1.0.1 < 1.1.0 < 2.0.0`, рівні версії, `v`-префікс,
  сміттєвий тег, коротший рядок (`1.1` проти `1.1.0`)
- вибір asset-а з фікстури JSON: правильний `browser_download_url`, поведінка
  коли asset з таким іменем відсутній, коли `assets` порожній
- `--version` друкує рівно `StintLogger <VERSION>` і не створює вікна
- перевірка `MZ` на файлі-не-exe
- підміна на тимчасовій теці з фальшивими «exe» (звичайні файли): після
  успішного проходу новий на місці, `.old` існує; при провалі гейта обидва файли
  лишаються недоторканими

Не покривається тестами й перевіряється руками (записати в план як окремий крок):
реальний цикл «старий exe качає новий, підміняє себе, піднімається, прибирає
`.old`» і автозапуск після цього.

## Ризики

- **Антивірус блокує щойно завантажений неподписаний exe.** Тоді гейт `--version`
  не пройде (або файл зникне) — оновлення скасується, старий лишиться робочим.
  Це саме та поведінка, яку ми хочемо; окремо не лікуємо.
- **Користувач тримає exe в Program Files.** Крок 3 (перейменування) впаде на
  правах — оновлення скасується тихо. Записати в README, що логер треба класти в
  теку користувача.
- **Реліз без asset-а `StintLogger.exe`** (наприклад, назва з версією у файлі) —
  оновлення просто не знайдеться. Тому ім'я asset-а фіксується як частина
  контракту релізу й записується в README.
- **Дві копії логера на машині.** Оновлюється лише запущена; друга лишиться
  старою. Приймаємо.
